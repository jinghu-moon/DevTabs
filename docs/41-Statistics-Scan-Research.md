# Statistics Scan Research

2026-11-12。状态：调研与优化路线，尚未替换生产扫描器，尚无候选库在本机的性能结论。针对 `Yue-GPUI-Component` 的统计截断问题，补充文档 35 的适用边界。

## 1. 必须修正的契约

当前磁盘扫描达到 200,000 项或约 3 秒就停止，源码扫描另有 200,000 项/5 秒限制。它们会漏掉未访问的目录；不能以此满足“准确且比老项目快”。文档 35 的小夹具对照只能证明当时 15,000 文件工作负载下的结果，不能推出大型真实项目已被完整统计。

优化目标是减少完成同一统计所需的 I/O、路径处理和调度成本。后台工作、进度展示和取消保持界面响应；限制并发、队列和进度发布频率，不按文件数量或总用时截断正常扫描。读失败必须报告，取消不能写入完成缓存。普通目录、构建产物、依赖目录都要计入既定磁盘口径；分类只影响展示，不能借分类省略遍历。

## 2. 本地参考：ffsearch1

只读研读 `D:/100_Projects/140_Archived/ffsearch1` 的当前 src/include/tests；未运行可执行文件、未改参考项目。以下以实现为准，不采用建议文档中的预计倍数。

| 机制 | 源码位置 | 对 DevTabs 的意义 |
| --- | --- | --- |
| 64 KiB 批量目录枚举 | `src/fs/scanner.cpp:116`、`:129` | 一批记录携带名称、类型及大小，减少枚举接口调用与包装成本 |
| 大小直接取记录中的 EndOfFile | `src/fs/scanner.cpp:308` | 统计逻辑长度无需逐文件打开句柄；不能与实际分配空间混淆 |
| 原生目录访问 | `src/fs/ntapi.cpp` | NtOpenFile 支持父句柄相对打开；NtQueryDirectoryFile 进行批量枚举。Win32 枚举路径也存在 |
| 目录任务并行、32 项批量提交 | `src/fs/scanner.cpp:432`、`:440` | 控制任务粒度，避免每个文件一个任务或每个子目录一次队列锁 |
| 线程私有缓冲与统计 | `src/core/thread_pool.cpp:3`、`src/main.cpp:203` | 减少路径/字符串临时分配及逐文件共享计数竞争 |
| 按阶段计量 | `include/ffsearch/metrics/stats.h` | 分开统计打开、枚举、转换、匹配、路径、任务及输出，区分墙钟与线程累计耗时 |

它当前有两条扫描路径，而不是单一的持久索引查询：

1. 卷根扫描可尝试 `FSCTL_ENUM_USN_DATA`，1 MiB 缓冲区枚举，文件名放连续池，以 flat vector 建父子索引，再在内存中匹配。
2. `src/fs/mft.cpp:222` 明确拒绝非卷根，随后在 `src/main.cpp:176` 的分派路径回退到目录遍历。因此扫描项目子目录时，值得借鉴的是目录遍历机制。

其 USN_RECORD 不包含文件长度；`src/fs/mft.cpp:470` 附近明确在大小/时间过滤需要时逐文件打开句柄查询。不能将仅搜索名称的耗时当作全项目大小统计耗时。当前实现中未找到读取 USN 变更流、ReadDirectoryChangesW 或持久索引增量维护；不能把名称中的 USN 枚举理解成已实现增量缓存。

DevTabs 不应照搬搜索规则系统、每文件 JSON 输出、整盘内存树或自制线程池。也不应将原生枚举中的错误悄悄当正常结束；取消、链接/重解析点、超长名称和缓冲记录边界需要独立行为测试。

## 3. 网络参考与库选择

| 项目 | 适合参考的部分 | 取舍 |
| --- | --- | --- |
| [dua-cli / dua-core](https://github.com/Byron/dua-cli) | Windows 原生批量枚举、工作窃取、有界批次、流式结果、元数据 | 磁盘遍历首选验证候选；`dua-core` 是可独立依赖的 MIT 库 |
| [dust](https://github.com/bootandy/dust/blob/master/src/platform.rs) | 避免逐文件打开、区分逻辑大小与分配大小、特殊文件处理 | 借鉴统计口径和元数据快路径；不引入整个 CLI |
| [pdu](https://github.com/KSXGitHub/parallel-disk-usage) | 并行目录汇总、进度与性能测量、可选硬链接处理 | 对照设计与测试；不为顶部几个目录创建完整搜索/图表系统 |
| [DiskSleuth](https://github.com/Swatto86/DiskSleuth) | 普通遍历与 MFT 分层、后台进度、紧凑树 | 是磁盘分析器参考；其 jwalk 依赖不是本项目新增库首选 |
| [jwalk](https://github.com/Byron/jwalk) | 早期并行遍历设计 | 当前已归档，README 明确推荐 dua-core，不作为新依赖 |

核对到的发布文档为 [dua-core 5.0.1](https://docs.rs/dua-core/5.0.1/dua_core/)，MIT，MSRV 1.88，符合本项目当前 Rust 1.98。其 [walk](https://docs.rs/dua-core/5.0.1/dua_core/fn.walk.html) 接受线程数、顺序、Options 与下降谓词；[Options](https://docs.rs/dua-core/5.0.1/dua_core/struct.Options.html) 支持有界批次缓冲。接入时再核对实际发布版本和锁文件，不使用仓库主分支尚未发布 API。

[dua-cli #359](https://github.com/Byron/dua-cli/pull/359) 使用 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` 与 64 KiB 缓冲，一批返回大小、类型、时间及身份。上游报告了自己的提速数据；它主要消除了原先逐项查询等开销，不代表 DevTabs 会获得相同收益。

DevTabs 的现有磁盘循环已用 `std::fs::DirEntry::metadata()`；[Rust 官方文档](https://doc.rust-lang.org/std/fs/struct.DirEntry.html#method.metadata) 明确说明 Windows 上无需额外系统调用。因此“换原生 API 必然大幅提速”不成立；文档 35 也记载此前单一原生封装未显示稳定收益。此次需要比较批量处理、并发调度和端到端成本，不能仅因 API 名称更底层就保留。

源码统计保留当前 `ignore` 的忽略语义。其 [WalkBuilder::build_parallel](https://docs.rs/ignore/latest/ignore/struct.WalkBuilder.html#method.build_parallel) 已提供并行 visitor，优先比较串行/并行版本；不为合并遍历而自行重写 `.gitignore`、嵌套否定规则和父目录规则。

## 4. 推荐的实现路线

1. 磁盘完整遍历优先验证 dua-core，先以 1/2/4 个线程作对照，保留同口径标准库完整遍历作为基准。不能拿旧版截断结果直接计算提速倍数。
2. 源码统计继续使用 ignore，比较其并行模式。源码与磁盘可独立发布结果，先出现源码统计不等于磁盘已经完成；避免每个选中项目各自创建占满所有 CPU 的线程池。
3. 聚合只保存所需一级目录/类别/语言汇总，不保存全部文件内容或完整文件索引。名称在目录边界确定、逐文件累计整数，避免逐文件解析完整路径和更新 UI。
4. 后台完整扫描，进度以例如 250 ms 的周期合并发布，而非逐文件发消息。界面分别显示扫描中、完成和读取错误；扫描中明确排名未完成，完成后再确认最大目录排名。世代不符立即取消，旧结果不能覆盖新项目。
5. `.` 表示根目录直属文件，展示为“根目录文件”；`crates` 按实际一级目录计入。构建/依赖仅单独分类，不能抢完一个截断预算导致普通目录遗漏。
6. 首轮完成后复用有来源/版本的结果；后续再以文件监听将受影响目录标脏并重算。监听溢出、断开或忽略规则变更要重新核对；根目录 mtime 不能独自证明后代文件未变。不能将缓存命中与首次遍历混算。

MFT 暂不作为项目子目录统计默认方案：卷级枚举与权限成本、NTFS 限定以及 USN 枚举缺少大小，均需额外机制。ffsearch1 自身也通过非卷根判断避免这条路径。若将来提供整盘索引，再单独评估直接 MFT 解析/USN 更新；不能混淆直接解析 MFT 与 FSCTL_ENUM_USN_DATA 的返回能力。

## 5. 验证和保留标准

- 完整性先行：超过 200,000 项、扫描超过旧截止时间、大小已知的 fixtures，断言文件数、总逻辑长度、分类和所有一级目录均正确；小项可以不在 Top 5，但不能没计入。
- 保持忽略/链接口径：Git/非 Git、嵌套 ignore、构建与依赖、Unicode/长路径、硬链接、重解析点、读失败、扫描中改名及取消；结果不能声称为整个变动目录的原子快照。
- 性能对照：同机 Release、相同覆盖范围、相同结果、交替运行标准库完整基线与候选，记录原始样本、首个结果/全部完成耗时、p50/p95、CPU 和内存；冷暖缓存分开。不用创建 fixture 的耗时代替扫描成本，也不通过排除 target 获得磁盘统计提速。
- 只读真实项目复核：`Yue-GPUI-Component`，确认 crates/docs/refer 的汇总与全量基准相符。正在构建时的变化单独标记，不能把不同时间的数据差解释成算法错误或性能提升。
- 原生/并行候选只在完整性正确且实测有稳定收益时接入；如果元数据不是热点，就继续定位路径分配、匹配、锁、发布与缓存，不能再次回到硬截断。
