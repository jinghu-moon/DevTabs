# Performance Optimization Workflow

日期：2026-11-10。仓库：<https://github.com/jinghu-moon/DevTabs>。

## 基线

Git 初始提交保存当前 DevTabs 0.4.0。它采用“完整处理已加载内容，绘制可视行”的方式，尚未实现可视区域按需高亮或 Markdown 块级按需布局。

升级前已有回归与测量摘要见 [12-Markdown-Renderer-Implementation.md](12-Markdown-Renderer-Implementation.md)。用于后续比较的原始测量摘要归档到 [performance/00-Rendering-Baseline.json](performance/00-Rendering-Baseline.json)。原始日志、可执行文件及完整采样保留在本地 `artifacts/`，不纳入源码仓库。

## 按顺序实施

1. 代码高亮按可视范围与预读行计算，使用词法状态检查点保证多行结构正确。
2. Markdown 建立块索引，按需布局可视块，并限制缓存；表格、公式和图形以完整块为单位。
3. 编辑后从修改处增量更新，在状态稳定后复用后续结果。
4. 保存保持冲突检查和全文原子替换，通过流式编码与写入减少整段临时副本。

每项独立完成和评估，不将尚未测量的后续改动混入同一优化提交。

## 快速滚动策略

代码预览与编辑器优先立即更新当前位置、行号和文本。缓存命中时立即显示高亮；缓存未命中时显示当前原文，停止滚动约 80 ms 后计算最终可视区及上下各 16 行预读。连续滚动合并需求，已过时任务逐行检查取消，不将上一屏颜色套到当前文本。初次打开无需等待该滚动延迟。

该策略延迟的是代码着色，不是界面绘制。Markdown 保持已经确定的块排版，不能在滚动时切成源码，避免行高变化造成位置跳动。其按块布局与缓存另行验证。

验证须同时检查快速滚动时当前文本可见、停稳后的颜色正确、实际触发的任务数量、输入与绘制耗时，以及包含等待时间的高亮完成延迟。80 ms 是待实测的初始参数，不作为通用最优值。

## 保留、提交和回退条件

- 先补充能够检出当前缺失或开销的测试、统计点及可复现负载，再实施优化。
- 在同一构建模式、相同文件和视口、相同采样条件下比较前后耗时与内存；同时记录冷启动、稳定状态及异常峰值。
- 统计须覆盖实际调用路径，不以减少循环次数或缓存命中率代替端到端收益。调试输出默认关闭，不记录文件内容。
- 保留现有功能及资源约束。核心指标改善，并且正确性与相关回归通过后，提交本项代码、测试、测量摘要和说明，推送到远端。
- 若收益未得到数据支持，或引入无法接受的回归，撤销本项实验改动；保留失败数据和结论。只撤销本项变更，避免覆盖其他工作。
- 实际终端和进程负载串行执行，避免相互争抢资源影响判定。变化不明确时先分析原因或补充测量，不挑选一次有利结果宣布成功。

## 文件范围与许可

提交源码、测试、正式文档、依赖锁文件及许可声明。参考仓库、构建产物、原始访谈、工具缓存和临时样本留在本地。需要长期比较的精简性能结果放在 `docs/performance/`。
