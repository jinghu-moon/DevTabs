# 快捷键统一重构与管理菜单设计

日期：2026-11-14。

状态：修订设计稿，依据本轮复审、源码复核及官方项目资料更新。本文定义待实施行为，不代表管理菜单、自定义配置或默认双绑定已经实现；本轮只更新文档。

## 0. 自评与本次修订

上一版的问题不是功能多，而是把主要篇幅给了通用框架，却没有把最常用的终端输入路径写成可实施、可验证的规则。保持完整重构范围，按日常场景和正确性依赖安排实施，不再另设削减功能的 MVP。

| 原稿不足 | 核对结果与修订 |
| --- | --- |
| “未注册就透传”没有实际占用清单 | 当前普通终端还会因侧栏存在而截获 Ctrl+P；新增实际/目标清单及清单外透传契约 |
| 前缀原键透传留待决定 | Claude Code 官方将 Ctrl+G 用于外部编辑器；明确双按前缀及显式命令，首个可使用版本就要实现，见 §6 |
| 默认所有 Fn 机械增加 Ctrl | Ctrl+F4 有关闭活动文档的既有语义；默认仅为本轮确认的 F3 增加 Ctrl+F3，其余逐项配置，见 §3.3 |
| 底栏优先显示 F3，冲突用户仍容易误按 | F3 双绑定默认显示 Ctrl+F3 在前；新增测试结果“一键设为首选显示”，见 §7.2、§7.5 |
| “外部保留”变成独立策略层 | 合并为删除绑定时附备注；移除独立 reserved schema 与合并层，见 §7.4、§8 |
| 整集合 override 冻结后续默认值 | 改为相对默认的 add/remove，首选显示独立存储；明确默认更新冲突策略，见 §8 |
| 按下/松开只写原则 | 给出物理身份、事件所有者、目标会话代次、失焦与重连状态迁移，见 §4.3 |
| 分支归类依靠人工承诺 | 增加生产键位分支审计清单和失败条件；导出修饰键精确化的行为差异，见 §12.1 |

## 1. 目标与已经确定的决策

快捷键首先要方便：常用功能能够一步触发，发生冲突时仍有同样直接的替代按法，不要求用户每次打开菜单选择“这次想做什么”。

本轮讨论确定以下规则：

1. **一个命令允许绑定多个按键。** `F3` 和 `Ctrl+F3` 可以同时绑定“编辑便签”，增加备用键不替换原键。
2. **精确识别修饰键。** `F3`、`Ctrl+F3`、`Shift+F3`、`Ctrl+Shift+F3` 是四个不同绑定；不能因为主键都是 F3 就执行同一分支。
3. **直接组合键优先，序列键可选。** `Ctrl+F3` 是同时按下的组合键；`Ctrl+G → N` 是分两步输入的序列。不能混用两种概念，更不强制把全部操作改成序列。
4. **保留外部软件的使用习惯。** 不默认安装全局键盘钩子、不注册系统级抢占热键、不根据“终端正在前台”推断用户不想截图。
5. **统一命令、匹配、作用域、菜单和提示的数据来源。** 不能只给总览增加一张键位表，其他区域继续独立硬编码。
6. **增加可点击的快捷键管理菜单。** 支持查找命令、多个绑定、自定义、删除并附备注、首选显示、恢复默认、冲突说明及按键测试。
7. **终端原生输入继续优先保真。** 未被当前上下文明确处理的事件沿现有 PTY 输入通道转发，不自动把总览的 F3 绑定扩展到 PowerShell、Codex 或 Claude 输入区。

### 1.1 F3 的最终使用模型

以总览的“编辑便签”为例，默认同时接受 `Ctrl+F3`、`F3`，提示优先展示 Ctrl+F3；匹配不分主备：

| 情况 | 用户按 F3 | 用户按 Ctrl+F3 |
| --- | --- | --- |
| 两组按键均正常到达总览 | 编辑便签 | 编辑便签 |
| 截图软件拦截 F3，Ctrl+F3 正常到达总览 | 由截图软件处理；DevTabs 不承诺收到 F3 | 编辑便签 |
| Windows Terminal 消耗 F3，Ctrl+F3 正常到达总览 | 由 Terminal 对应绑定处理 | 编辑便签 |
| 焦点在源码编辑器 | 编辑器的下一处匹配 | 编辑器的下一处匹配 |
| 焦点在内部终端，未配置额外终端区绑定 | 若到达 DevTabs，交给终端程序 | 若到达 DevTabs，交给终端程序 |

按键到达的承诺边界统一见 §10.3。截图与便签同时触发时，用户可删除本地 F3 并附“截图使用”备注，保留 Ctrl+F3；这与仅调整首选显示是两种不同操作。

### 1.2 不采纳为默认方案的做法

- 不把“发送按键”菜单当作日常执行快捷操作的必经路径。
- 不在每次按下冲突键时弹窗询问归属。
- 不默认屏蔽截图、输入法或 Windows Terminal 的快捷键。
- 不宣称换成 Ctrl 修饰就一定无冲突；备用组合键本身也可以修改。
- 不静默删除原绑定，也不在发现重复时自动抢占其他命令。
- 不把本地“忽略此键”描述成“重新触发外部软件”；DevTabs 无法替没有收到事件的其他程序补做截图。

已确认的典型问题：

- 总览有 `KeyCode::F(3) => Command::Note` 这类仅匹配主键的分支。Ctrl+F3 当前即使碰巧生效，也不是一个可管理的独立绑定。
- 部分组合键通过 `modifiers.contains(CONTROL)` 判断，可能同时接受额外 Alt/Shift；另一些位置又使用完全相等判断，行为不统一。
- 鼠标命令部分复用模拟按键。修改默认键后，点击入口可能失效或执行另一个功能。
- 帮助、底栏、工具栏和命令菜单存在独立按键字符串，无法保证随自定义配置更新。
- 相同 F3 在总览表示便签、在编辑器表示下一处匹配，这是合理的作用域复用，不能当作全局重复绑定禁止。

重构范围覆盖以上全部 DevTabs 管理的快捷操作，包括局部弹窗。原生终端程序自身的快捷键、Windows 保留组合键、输入法配置和外部软件全局热键不由 DevTabs 统一重定义。

### 2.1 普通终端输入区的实际占用与目标清单

本表限定为：工作区普通模式、焦点在已连接终端、没有弹窗/选择/拖动状态。菜单状态拥有自己的按键，不能混写成普通终端占用。

| 按键 | 当前代码事实 | 重构后默认 |
| --- | --- | --- |
| Ctrl+G | `App::key` 在终端路由前进入前缀模式；当前 contains(CONTROL) 还可能接受额外修饰键 | 精确 Ctrl+G 进入命令模式；支持更换或关闭终端区前缀入口 |
| Ctrl+P | `App::key` 对存在的 Sidebar 有特例；`explorer_key` 会在树焦点判断之前调用 quick_open | 普通终端默认透传；files.quick_open 的 Ctrl+P 保留在文件区域，用户可显式扩展到终端区，不为保留旧行为而抢 CLI 历史导航 |
| F1–F12，包括 F3 / Ctrl+F3 | 普通终端路径没有总览功能键处理 | 继续交给终端程序；不会因总览新增别名而扩大占用 |
| Ctrl+C、Ctrl+Z、Ctrl+S、Ctrl+F、Tab、Enter、方向键、普通字符 | 在普通终端上下文中沿 forward_key 处理，前提是事件实际送达且目标可用 | 保持透传；受管前缀及用户显式新增项之外，没有隐式工作区拦截 |

额外状态的输入权要在生成目录中独立列出：命令前缀、终端会话菜单、冻结输出选择、未保存提示、审阅、任务表单、移动/缩放等。当前选择模式会消费更多按键；窗口无可用目标时也不能声称已完成透传。

目标默认截获表必须从有效注册表导出，普通终端区只有 Ctrl+G。Ctrl+P 默认走原生终端路径；删除 Ctrl+G 终端区入口后，改用可点击命令菜单或自选组合键。`terminal.input` 的键位可配置为零占用；改动旧 Ctrl+P 行为须进入升级前后差异报告，文件查找能力继续保留。

契约测试枚举默认清单之外的键及修饰键：VT 模式对照既有编码器输出；Win32 模式对照原始记录字节、顺序、重复次数和配对事件。透传不能简单解释为 UTF-8 字符串原样复制。

## 3. 统一命令与绑定模型

### 3.1 命令 ID 是唯一执行入口

新增共享快捷键模块，建议组织为 `src/shortcuts.rs` 及其 `registry`、`binding`、`context`、`resolve`、`config`、`menu` 子模块；文件划分可按代码规模调整。

每个业务命令注册：

| 属性 | 约定 |
| --- | --- |
| `id` | 稳定、无语言依赖，例如 `overview.note.edit`、`editor.search.next`、`shortcuts.open` |
| `label_key` / `category_key` | 复用中英文文案体系 |
| `contexts` | 明确允许执行的上下文，不能通过命令前缀字符串猜作用域 |
| `default_bindings` | 显式绑定集合，可以为空、单个或多个 |
| `enabled` | 基于当前状态判断，不在每个键位分支重复实现 |
| `repeat` | `once` 或 `repeatable` |
| `exposure` | 可重绑命令、控件导航或固定取消/恢复机制 |
| `handler` | 调用现有业务动作，保留保存、确认、异步请求和目标身份检查 |

键盘、鼠标、命令面板、工具栏和帮助中的可执行入口都解析到命令 ID。现有 `Overview::command`、`Sidebar::command` 等可保留为业务适配器，不要求合并所有业务枚举。

同一个命令有两个绑定，只执行一次。注册时按“命令、上下文、按键序列”去重，不允许两条等价记录导致双重启动或重复保存。

### 3.2 按键表示

内部采用结构化表示：`KeyChord { key, modifiers }`。首期上限明确为一个 chord，或“已声明前缀 + 一个后续 chord”，共两步；没有任意长度序列。所有修改使用同一解析器、格式化器和校验器。

- 展示：`F3`、`Ctrl+F3`、`Ctrl+Shift+N`；序列展示 `Ctrl+G → F`。
- 保存：单个组合键用字符串，一条序列用字符串数组；不使用含义不清的空格拆分。
- `Ctrl`、`Control` 的输入别名可接受，保存时统一为 `Ctrl`；修饰键统一按 Ctrl、Alt、Shift、Super 顺序输出。
- 左右 Ctrl/Alt/Shift 在普通 UI 绑定中视为同类，原始 Win32 记录仍原样保留给 PTY。
- `Shift+Tab` 与 `BackTab` 统一为同一种导航绑定；不能同时注册成两个不同动作。
- 字母大小写和 Shift 由同一套事件/配置归一化规则处理。保留现有 `f` 与 `Shift+F` 的不同语义；不能简单将所有字符转小写并丢弃 Shift。
- `+` 使用 `Plus` 等无歧义键名，字面 `+`、`!` 等按录制到的逻辑字符归一化；不把键盘布局产生字符所需的物理 Shift 误算成额外命令修饰键。
- 中文、组合字符、IME 上屏文本、粘贴事件按文本处理，不分解成快捷键序列；AltGr 等文本输入也不得仅凭 Ctrl+Alt 位被当作命令。无法可靠区分的平台组合标为不建议绑定。
- CapsLock、NumLock 等锁定状态不参与命令相等判断。Super/Win 等未被当前输入通道可靠报告的组合不承诺可用，管理菜单须显示支持边界。

本轮必须建立事件归一化夹具，覆盖 Windows UnicodeChar、大小写、Shift、AltGr 和控制字符；不能只测试配置字符串解析。

默认避让清单如下，录制和文本输入使用同一校验。具体系统/输入法配置可能改变它们的用途，提示应为风险说明而非“已检测到占用”。Windows 常用快捷键和微软拼音资料见 [R6]、[R7]。

| 组合 | 管理页规则 |
| --- | --- |
| Ctrl+Space、Ctrl+Shift+Space | 提示可能用于输入法切换或文本功能；默认不分配，用户明确确认后才允许保存可表示的组合 |
| Shift+Space、Ctrl+Period | 提示微软拼音中全/半角及中英文标点切换的常见用途；文本区默认避让，用户自定义时显示风险 |
| Ctrl+Shift、Alt+Shift 单独组合 | 作为修饰键组合/输入语言切换风险提示；首期不支持仅修饰键绑定，不将它误录为普通 chord |
| Win/Super 组合 | 提示系统占用及当前输入通道报告限制；默认不分配，无法可靠表示时拒绝保存 |
| Alt+Tab、Alt+Esc、Win+Space、Ctrl+Esc | 提示窗口切换或系统功能风险；默认不分配，不承诺一定能送达终端 |
| Ctrl+Alt+Delete | 系统安全组合，拒绝作为 DevTabs 绑定；不能用“保存成功”暗示可以接管 |
| Ctrl+F4、Alt+F4 | 提示关闭文档/窗口的常见语义；不作为任意命令的自动备用键，文本配置仍需相同校验 |

上述警告只在添加/修改配置时出现，不在日常每次按键时弹窗，也不更改输入法设置。

### 3.3 默认双绑定策略

1. 保留现有有效、明确的默认快捷键，修饰键精确化的差异按 §12.1 导出，不能把所有旧的宽松匹配都当作正式别名。
2. 本轮明确增加的默认双绑定只有两个命令：总览 `overview.note.edit`、编辑器 `editor.search.next`，各自在原有区域接受 `Ctrl+F3` 与 `F3`，首选显示 Ctrl+F3。
3. 其他 F1–F10 保留原有显式默认值，用户可以追加 Ctrl+Fn 或其他组合；新的内置备用键须逐项说明常用需求、检查内部冲突和系统语义。尤其不自动将 Ctrl+F4 绑定为重命名/上一处匹配。[R6]
4. 所有别名都必须是注册表中的明确记录，管理页“有效绑定”完整展示并允许单独删除；配置文件只保存用户相对默认的差异，无需把默认别名再写一遍。运行时没有“Ctrl+任意功能键视为裸功能键”的降级规则。
5. 只改变展示首选不会改变有效绑定、命令优先级或按键消费；日常底栏优先使用用户指定项，再使用命令的默认首选。拥有 Ctrl+Fn 别名时默认优先显示该项，没有则显示原键，不虚构绑定。
6. Enter、Esc、方向键、Tab、普通字符及已有 Ctrl/Alt 组合按原业务含义显式登记；例如 Ctrl+Enter 的批量启动保持独立。
7. 添加、删除或排序都不要求两个绑定同时存在；备用键也可能受外部影响，管理页提供测试与自定义入口。

“应用级”仅表示 DevTabs 内部共享的命令范围，不表示 Windows 全局热键。

### 4.2 分发顺序

每个事件只走一次统一路由：

1. **事件分类与原始记录保留**：区分文本/粘贴、按下、重复、松开、焦点与尺寸事件；不要先删修饰键再匹配。已有按下所有者的 Up/重复事件先按 §4.3 处理，只有新的按下周期进入下列命令匹配，避免模态抢走原终端的 release。
2. **顶层独占状态**：按键录制/测试、未保存提示、确认框、模态菜单和移动缩放等状态先处理。独占状态未匹配的命令不得落到背景界面。
3. **序列等待状态**：只在已经明确进入前缀模式时匹配下一步，按第 6 节处理取消和失焦。
4. **当前焦点局部命令**：从最具体上下文查找，包括选择、编辑查找、图片等。
5. **允许传播的父级命令**：只匹配显式允许在此上下文生效的工作区/总览共享命令。编辑输入区和模态状态禁止无条件父级兜底。
6. **原生控件与终端兜底**：文本/编辑导航交还对应控件；`terminal.input` 中剩余按键及必要原始记录继续经 `App::forward_key` / `input::key` 转发。

匹配器返回明确结果：`Execute(command)`、`AwaitSequence`、`Handled`、`TextInput` 或 `ForwardTerminal`，不能再靠多层 `Option` 和调用顺序猜测是否已消费。

Ghostty 将 unconsumed（执行且继续发送）与 performable（可执行才消费）显式区分，[R5] 说明消费语义需要成为模型的一部分。DevTabs 自有业务命令采用单一所有者：执行即消费；不引入“执行便签同时向 shell 发 F3”的通用选项。Ctrl+C 选择复制等既有条件行为通过显式上下文表示。

- 已命中但当前不可用的命令：显示简短原因并消费该触发键，不穿透到另一个危险命令或终端。
- 选择状态中的 Ctrl+C 只复制当前明确选区；终端输入区未注册拦截时仍保留原生 Ctrl+C 行为。
- 顶层菜单可查询业务命令可用性，但不绕过未保存提示、三秒强制终止限制、任务身份或恢复队列审阅。
- 允许父级和子级复用同一键时，子级覆盖必须在注册表声明并在菜单显示；同一有效层出现两个不同命令则是阻断性冲突。

### 4.3 重复、松开和焦点变化

本节是输入保真门槛，先于菜单和全量迁移完成。当前 `App::consumed_keys` 是 `HashSet<KeyCode>`；`Events::key` 在生成通用事件时还过滤单独修饰键记录。两者不足以承担以下契约，不能只把集合键类型换一下就宣称解决。

事件适配层应在原始记录被过滤/拼接之前保留物理身份、按下状态、控制键快照和原字节；使用 `KEY_EVENT_RECORD` 的 vk、scan code、ENHANCED_KEY 区分物理键，字段依据见 [R8]。控制台记录没有提供设备 ID，设计不虚构多键盘身份。

```rust
// 目标结构示意；不代表现有类型已经实现。
struct PhysicalKey { vk: u16, scan: u16, enhanced: bool }
struct TerminalTarget { session_id: String, connection_generation: u64 }
enum PressOwner {
    Ui { context_generation: u64 },
    Terminal { target: TerminalTarget, wire_mode: WireMode },
    SequencePending { target: Option<TerminalTarget> },
    SuppressUntilUp,
}
struct ActivePress {
    owner: PressOwner,
    repeat_policy: RepeatPolicy, // UiOnce / UiRepeat / TerminalRaw / SendOnce
    first_down: RawKeyRecord,
    last_control_state: u32,
    input_epoch: u64,
}
struct KeyLedger {
    held: BTreeMap<PhysicalKey, ActivePress>,
    // 只记已经实际发给该终端的 Win32 down；包括适配器确实发送的修饰键。
    delivered_down: BTreeMap<TerminalTarget, BTreeMap<PhysicalKey, RawKeyRecord>>,
}
```

`PhysicalKey` 不包含当前 modifiers：先松开 Ctrl、再松开 F3 时仍须找到同一次 F3。目标采用稳定会话身份和连接代次，不能用当前数组下标；协议变化时 release 按 down 时的 wire mode 完成或执行显式重置，不能发一半 Win32、一半 VT。

| 事件 | 必须执行的状态转换 |
| --- | --- |
| 首次 Down，物理键不在 held 中 | 运行一次路由；记录 Ui、Terminal 或 SequencePending 所有者。只有成功发送后才写 delivered_down |
| 同一物理键再次 Down | 视为重复，沿原 owner 和 repeat_policy 处理；once/SendOnce 不重复，repeatable 导航只在原 context_generation 仍有效时重复，否则转抑制；TerminalRaw 保留次数。不能靠 wRepeatCount=1 推断一定是全新按下 |
| Up | 先查 held：Ui/SequencePending 消费并移除；Terminal 发给原目标再移除；SuppressUntilUp 仅移除。不会因 UI 已关闭或当前焦点改变而重新运行命令匹配 |
| 未找到匹配 Down 的 Up | 没有任何目标记录已收到对应 down 时，作为未配对事件丢弃并计数；不向当前终端猜发 release |
| 菜单/模态关闭或区域焦点改变 | 取消未完成序列；Ui/SequencePending 可转 SuppressUntilUp，Terminal 保留原 owner 至 Up。若须抑制 Terminal，先平衡实际已发送的 Win32 down 再转抑制，不能只改 owner 丢掉 release；**不能直接 clear held**。新按键周期才使用新焦点 |
| 原终端切换到另一会话 | 已发送 down 的 release 仍归原 session/generation；不得把旧键的 Up 发给新会话，也不因补发 release 将旧终端重新设为 live/focus |
| 窗口失焦 | 取消序列。对 delivered_down 中仍存活目标的 Win32 已送达键，发一次目标内平衡 release；普通键先于修饰键，逐步更新 control-state。随后转为 SuppressUntilUp，防止稍后真实 Up 再发一次 |
| 重新获得焦点 | 新增 input epoch；仅对账本挂起键做辅助状态核对。GetAsyncKeyState 最高位置位可支持“仍按住”的判断；返回 0 也可能是桌面/访问权限失败，不能冒充已观察到 Up。未知状态保留 SuppressUntilUp，不凭查询结果向 PTY 合成输入；不使用不可靠的最低位。[R9] |
| 目标断开、退出或重连 | 旧 generation 的记录终止；存活原连接可做目标内平衡，不可达时记录无法补发并丢弃。旧 Up 不得进入新连接；新会话不继承旧键盘状态 |

补充协议规则：

- Win32 的补发只通过指定 PTY 输入通道，依据实际 delivered_down，构造一次 `bKeyDown=false` 记录；不使用系统 `SendInput`，不给外部应用制造键盘事件。
- 独立 Ctrl/Alt/Shift 记录须进入账本更新。Win32 适配器若向终端发送它们，也承担配对责任；不能只记 modifier 位就声称发过独立 Down。
- VT 路径按现有能力忽略 release，不合成控制字符“释放 Ctrl”，不引入终端键盘协议升级；原始 Windows Unicode 代理对和重复记录在转发时保留顺序。
- 单独修饰键 Down 可以先到终端，再由带修饰键的业务 chord 被 UI 消费。这时修饰键 Up 仍应平衡其原目标，业务主键 Up 则留在 UI，不能粗暴吞掉整组。
- 缺少原始物理信息的平台使用适配器提供的稳定键身份并标示能力限制；测试不把逻辑 KeyCode 回退宣传成物理级保证。
- 失焦后已错过 Up、且辅助查询无法确认状态时，保守抑制可能吃掉该键恢复后的第一次按下。提供可见提示“松开后再按一次”：这一轮 Down 继续抑制，真实 Up 清除记录，下一轮恢复。该失败路径必须测试；不能为了避免一次重按而把旧 release 或业务动作送给新目标，也不承诺能重建外部截获期间的完整物理历史。
- `Event::Paste`、IME 文本和鼠标命令走各自通道；修饰键账本只维护实际键盘记录，不把粘贴正文拆成 Down/Up。

必须验证的最小轨迹：① Ctrl Down → F3 Down（UI）→ Ctrl Up → F3 Up；② 按下 Enter 打开弹窗后松开；③ 终端 A Down → 切终端 B → Up；④ Down → 窗口失焦 → 收不到 Up → 恢复焦点；⑤ 长按 Ctrl+G 产生重复 Down；⑥ 原目标断开后旧 Up 到达。逐步断言 owner、发送目标和字节，不能只断言最终菜单状态。

## 6. 前缀模式与直接组合键并存

### 6.1 前缀原键有首期必做的出口

保留可配置的 Ctrl+G 命令入口；前缀只是绑定的一种形式。Claude Code 官方文档确认 Ctrl+G 可打开外部编辑器，[R1] 因此“发送前缀原键”不是可选优化，也不留待迁移再决定。

参考 WezTerm 的 leader + SendKey 和 tmux 的 send-prefix [R2][R3]，注册以下两个显式命令，均绕过 UI 快捷键解析器，直接写入确定的终端目标：

| 命令 | 默认触发 | 语义 |
| --- | --- | --- |
| `terminal.send_prefix` | Ctrl+G → Ctrl+G；命令菜单也有可点击项 | 向进入前缀时的终端发送一次 Ctrl+G，保持终端程序原生用途 |
| `terminal.send_quick_open_key` | 默认无绑定；用户扩展终端区 Ctrl+P 时可添加 Ctrl+G → Ctrl+P，菜单提供出口 | 只在用户确实拦截 Ctrl+P 时需要；普通终端默认直接按 Ctrl+P 即透传，不额外占一组序列 |

普通 `Ctrl+G → g` 继续是轮次审阅，`Ctrl+G → p` 继续返回总览；带 Ctrl 的第二步必须先按完整 chord 精确匹配，不能先匹配 `Char('g')` 或 `Char('p')`。当前代码对 g 的匹配顺序正是不能假定“双按 Ctrl+G 已可透传”的原因。

默认终端区 Ctrl+G 是可以删除的独立入口；删除不影响鼠标菜单，也不改变用户另行绑定的入口。若只想让 CLI 直接收到 Ctrl+G，删除这一条即可，无需学双按。自定义前缀后，`terminal.send_prefix` 的默认序列自动变为新前缀按两次；用户显式添加的 Ctrl+P 出口第二步仍表示其发送的 Ctrl+P。

### 6.2 发送与取消的精确行为

- 进入时捕获稳定 terminal target。目标切换、退出或 connection_generation 改变立即取消序列；不会将前缀补发给新 Agent。没有可用终端时两条发送命令显示不可用。
- 第二次前缀必须是新的主键按下周期：第一次 G 的 Up 已到达后，再次 G Down 才成立；可以保持 Ctrl 按下。长按一次 Ctrl+G 的重复记录不能变成“发送前缀”。
- 键盘发送使用第二个 chord 的记录生成一次输入并把其 owner 转给原终端，repeat_policy 为 SendOnce：该记录的发送重复数规范为 1，随后长按产生的重复 Down 被消费，真实 Up 按账本归同一目标。除重复数这一显式发送语义外保留原始字段；不重新走 UI resolver，因此不会递归开菜单。Ctrl+G 和 Ctrl+P 两个出口遵循同一规则。
- 鼠标选择“发送前缀原键”时，通过协议适配器产生一组平衡的主键 Down/Up；VT 只生成一次对应控制输入，Win32 生成完整配对并依据账本处理修饰键。不把第一次已被 UI 消费的事件直接混入新焦点。
- 原始事件优先；只有显式“发送”命令可构造终端输入。它不调用系统 SendInput，不触发系统级截图，不承诺绕过终端程序自身的快捷键。
- 命令模式默认没有自动超时；Esc、点击外部或失焦取消时，只重置序列状态，按 §4.3 保留待配对按键的 owner/tombstone。
- 无效第二键退出并提示；已用作命令输入的序列不重放给 shell。退出后的下一个全新按键周期正常路由。
- 首期序列恰为前缀加一个后续 chord。前缀不能同时是立即执行的独立业务命令，纯修饰键也不能作为前缀。
- 文本编辑/表单中是否启用前缀要显式声明，普通字符按文本输入；工作区菜单的点击执行始终走命令 ID。

验收必须包含 Claude Code Ctrl+G 外部编辑器、PowerShell/其他 CLI 的 Ctrl+P、连续双按、长按、切会话与目标断开。外部编辑器能否成功启动还取决于 CLI 的编辑器配置，测试应分别记录“事件已送达”和“编辑器启动结果”。

## 7. 快捷键管理菜单

### 7.1 入口与布局

新增稳定命令 `shortcuts.open`，入口至少包括：

1. 总览命令面板中的“快捷键管理 / Keyboard shortcuts”。
2. 工作区命令菜单中的“快捷键管理”。
3. 总览与工作区现有设置/更多菜单中的可点击项。不得依赖唯一一个可能被截获的快捷键才能打开管理页。

打开设置不要求新增一组固定全局组合键。用户可自行给 `shortcuts.open` 绑定直达键；前缀菜单入口继续支持鼠标。

使用现有 TUI 弹层样式，包含：

| 区域 | 内容 |
| --- | --- |
| 顶部 | 标题、搜索框、关闭按钮、未应用标识 |
| 筛选 | 全部 / 当前区域 / 已修改 / 未绑定 / 内部冲突 / 含删除备注 |
| 命令列表 | 功能名、作用域、有效绑定集合、默认/自定义来源、状态 |
| 当前命令详情 | 功能说明、允许区域、当前不可用原因、全部绑定、默认值及覆盖关系 |
| 操作区 | 添加/修改绑定、删除并可附备注、设为首选显示、恢复当前命令、按键测试 |
| 底部 | 应用、取消、恢复全部默认、备份/导入/导出 |

宽窗表格并列显示，窄窗改为列表加当前项详情；按终端单元格宽度截断，不能让长命令名挤掉所有按键。每个操作有鼠标入口，Tab 顺序清楚。

管理页自己的搜索、Tab、方向键、Enter、Esc 为固定控件导航，不能被当前待编辑绑定覆盖。按键录制时这些键可作为录制内容，取消/确认通过可点击按钮完成，避免 Esc 永远无法录制或把 Enter 误当确认。

### 7.2 F3 双绑定示例

管理页当前项：

| 功能 | 生效区域 | 绑定 | 来源 |
| --- | --- | --- | --- |
| 编辑便签 | 总览 | Ctrl+F3、F3 | 默认 |
| 下一处匹配 | 源码编辑器 | Ctrl+F3、F3 | 默认 |

同一个命令下两个键并列显示，不使用“主键失效才自动启用备用”的模式。只要事件到达且上下文匹配，两个键均有效。

菜单推荐展示 `Ctrl+F3 / F3`；底栏空间不足时只显示 Ctrl+F3。首选显示是独立字段，用户可一键更改；其他默认 Fn 只有在确有 Ctrl 别名时才显示该项。更换首选不删除 F3，也不消除截图与本地动作同时发生的可能；删除不需要的本地绑定才会停止该动作。

### 7.3 录制、添加与修改

1. 用户先选命令及允许的作用域，再选择“添加”或“修改”。添加只追加，不清空原集合。
2. 录制区进入独占模式，实时显示实际收到的键名与修饰键，忽略仅修饰键按下；被录制的保存、删除、关闭等命令不执行。
3. 组合键在一个完整按键周期后形成候选；选择“序列”时显式录制前缀和第二步。
4. 同时提供文本编辑模式，用于录制不到的外部冲突键或无歧义输入 `Ctrl+F3`。未收到事件不得解释为绑定格式错误。
5. 保存前解析、归一化并校验支持范围和内部冲突；重复添加当前命令已有绑定只提示，不复制一条。
6. “修改”只替换选中那一条；“删除”只移除选中绑定，可选备注如“截图软件使用”。允许某个命令无快捷键，鼠标和菜单仍可执行。
7. 对仅修饰键、系统/输入法风险组合按 §3.2 统一处理，文本输入和导入也使用同样校验，不让用户绕过录制警告误以为一定可用。

### 7.4 冲突、删除和备注

冲突页只准确报告 DevTabs 知道的事实：

| 类型 | 显示 | 处理 |
| --- | --- | --- |
| 同一命令、同上下文、同按键 | 已存在 | 去重，不报业务冲突 |
| 不同命令、同时有效的相同绑定 | 内部冲突，列出双方及区域 | 阻止应用；提供取消、换键、明确替换 |
| 父子上下文显式覆盖 | 区域覆盖，列出当前生效者 | 可接受，必须有声明和可见说明 |
| 互斥上下文复用，如总览/编辑器 F3 | 在不同区域使用 | 允许，不作为错误 |
| 删除绑定时填写截图/输入法备注 | 已删除，附用户备注 | 对该命令/区域移除这条绑定，不推断外部占用事实 |
| 测试未收到按键 | 未收到，原因未知 | 提示检查外部软件/宿主，不自动猜软件名 |

“替换”必须显示将从哪个命令的哪个区域移除哪个键，保留其他别名。不提供不清楚后果的“仍然强制保存”。

“外部保留”不再是单独 UI 概念或解析策略。操作统一为**删除这条绑定，可附备注**：

- 删除默认键保存为 remove；删除用户新增键从 add 中去掉。备注不参与匹配，不制造全局禁用表。
- 每次删除明确作用的命令和区域；可批量勾选多个同键项，先展示差异。删除总览 F3 不顺带删除编辑器 F3。
- 删除后该 chord 没有本地命令处理时，终端区正常透传、文本区交给控件，不主动替外部程序执行动作。
- 恢复绑定或恢复默认时，清除对应 remove，显示旧备注并由用户决定保留说明或删除；备注不能再次禁用已恢复键。
- 删除全部当前绑定与“禁用此命令在此区域的所有快捷键”区分：前者只处理当前集合，后者使用 §8 的 disabled，未来默认键也不再加入。
- 未修改的 F3 / Ctrl+F3 双绑定继续同时可用，不需要用户提前声明外部软件名单。

### 7.5 按键测试

按键测试是诊断工具，不是业务执行入口：

- 记录到达 DevTabs 的按键、修饰键、Press/Repeat/Release、当前上下文、预计命令和未匹配原因。
- 显示按键在目标上下文的解析结果；测试弹层独占输入但不把所有结果都解释成 `shortcuts.test` 的业务命令。
- 不执行预计命令，不把测试输入转发给 Agent / shell。
- 无事件时仅显示“尚未收到按键”；可以提示外部截获是可能原因，不能认定冲突存在，更不能自动列出占用软件。
- 测试区域注明：外部全局热键仍可能触发，DevTabs 未对外部软件做屏蔽。
- 默认仅保留当前测试会话的有界内存记录，不后台记录普通输入、不持久化键盘日志。
- 结果对应一个明确命令且测试 chord 已是其有效绑定时，提供“设为首选显示”。点击只更新首选草稿，经应用后同步底栏/帮助；不删除其他键、不新增绑定、不执行该命令。
- 已收到但未绑定的 chord 只能进入“给选中命令添加绑定”流程；无事件、冲突、多个未解决候选时禁用首选操作。也可以在绑定列表直接更改首选，避免“无法收到键就无法设置”的循环。

## 8. 配置格式、覆盖与持久化

### 8.1 配置所有权

绑定是用户级偏好，首期不放进项目 `.devtabs` 配置、项目 Profile、恢复日志或宿主 IPC。不同项目不应悄悄改变 F3 含义；多个前端通过现有 Config 更新/锁/原子写机制协调。

中央配置容器、注释保留、字段归属及开发期重构原则见 [设置与统一配置设计](53-Unified-Configuration-Design.md)。只保留容器根 schema，不增加 shortcuts 组件版本；快捷键差异和首选显示只属于用户级。

在新的用户设置中增加 `shortcuts`，缺失时使用代码默认注册表。采用**相对当前默认值的增删差异**，其必要性来自默认值和用户意图需要独立演进；VS Code 的规则可作资料参考 [R4]，不作为照搬其运行时顺序或 JSON 语法的理由。以下为新 config.toml 的片段，不提供旧格式兼容：

```toml
schema = 1

[shortcuts]
prefix = "Ctrl+G"

[[shortcuts.bindings]]
command = "overview.note.edit"
context = "overview"
add = ["Ctrl+Alt+N"]
remove = ["F3"]
preferred = "Ctrl+F3"
notes = { "F3" = "截图软件使用；仅删除此命令的本地 F3" }

[[shortcuts.bindings]]
command = "editor.search.next"
context = "editor"
preferred = "Ctrl+F3"

[[shortcuts.bindings]]
command = "files.quick_open"
context = "terminal.input"
disabled = true

[[shortcuts.bindings]]
command = "shortcuts.open"
context = "workspace"
add = ["Ctrl+Alt+K"]
```

示例新增键只是格式演示，仍经过内部冲突及输入法风险校验。`add` 支持单 chord 或 `["Prefix", "L"]` 两步序列；Prefix 为受管前缀引用，普通序列只用在第一步。`terminal.send_prefix` 的受管默认绑定特例为 `["Prefix", "Prefix"]`，两步都随前缀更新，仍要求两个独立主键周期。文本编辑器和录制 UI 均保存同一结构。

对一个 command/context，设当前内置集合为 D、用户 add 为 A、remove 为 R：有效集合 `E = (D ∪ A) − R`；disabled=true 时 E 为空。A/R/notes 默认空，disabled 默认 false。相同条目去重，A 与 R 有交集时报错，避免“添加成功但实际仍删除”。删除非现有键的 R 保留为 tombstone 并给说明，以便未来默认值仍尊重该删除。

同一 command/context 只允许一条差异记录。preferred 是对有效绑定的引用，仅影响展示；指向已删除/失效键时提示并按当前默认首选、其他有效键顺序回退，不能因此恢复那个键或使启动失败。

工作区默认序列和用户明确选择“受管前缀”的序列都保存 Prefix 标记。更换前缀只重新展开该标记，不字符串替换所有 Ctrl+G；`terminal.send_prefix` 的发送值随之更新。配置只支持当前受管前缀和一个后续 chord，不能悄悄启用额外前缀。

父级绑定在当前子区域继承后再计算该子区域差异；remove/disabled 形成该 command/chord 的遮罩，禁止在回退父级时重新引入它。例如只在 overview.projects 删除 F3，仍可保留详情区域 F3。每个命令允许的父/子区域集合由注册表声明，用户不能通过任意 context 字符串提升权限。

合并顺序：当前默认注册表 → 合法上下文继承 → 用户差异/遮罩 → 冲突与可达性校验 → 编译索引 → 选择首选显示。notes 只用于解释，完全不进入匹配器；没有独立 reserved 层。

### 8.2 默认值演进与恢复

| 更新情况 | 行为 |
| --- | --- |
| 默认新增 Ctrl+其他键，用户仅删除 F3 | 新默认正常进入 E，F3 的删除持续生效 |
| 默认移除旧键 | 旧默认随更新消失；用户若显式加进 A 则继续保留 |
| 用户只设 preferred | 后续默认增删照常生效，显示偏好不冻结集合 |
| 用户逐条删除当前全部默认键 | 仅 R 中的键被删；未来新默认仍可加入，菜单明确说明 |
| 用户选择 disabled=true | 此区域保持没有该命令的快捷键，包括未来默认新增；菜单仍可执行业务命令 |
| 新默认与现存用户绑定碰撞 | 用户显式设置优先，抑制冲突的默认候选并显示升级提示；不覆盖用户。两个显式用户命令冲突仍阻止应用 |
| 命令 ID/作用域退役 | 差异和备注保留为失效项并定位说明；开发期不增加历史重命名映射或自动迁移 |

默认构建本身必须无冲突。升级时的默认抑制是有来源记录的例外，不是一般“冲突时先来先得”；有效表应显示被抑制项，允许换键后恢复。恢复当前命令清除其 A/R/disabled/preferred；恢复全部清除整个用户差异。备注按用户选择保留为历史说明或一并清除，均不影响匹配。

配置文件只保存差异，管理页完整显示“当前默认 / 用户新增 / 用户删除 / 有效 / 首选”。这就是旧稿“用户能看到别名”的准确含义。导出用户配置和导出完整有效目录应为两种明确操作，后者不能被误导入为冻结的默认集合。

### 8.3 应用、取消与失败

- 管理菜单使用草稿，“应用”前校验整张有效表；取消不写配置、不改变运行时绑定。
- 应用先通过现有带锁更新读取最新 Config，只合并快捷键字段，保留其他前端保存的项目、主题和布局设置。
- 保存成功后一次性替换当前前端内存索引；失败保留原有效表和编辑草稿，不出现“界面显示改了、实际按键没改”的状态。
- 启动时快捷键字段无效，不使整个应用无法进入：快捷键字段应在独立校验边界解析，回退内置默认并提供具体错误及打开管理菜单入口。配置文件其他部分的现有错误策略不被静默改变。
- 未知命令/上下文按失效配置保留，标示未应用并允许用户修正，不擅自删除；这用于手改诊断，不承担历史版本兼容。
- 首期不要求增加持续配置文件监听；当前窗口应用后生效，其他已打开窗口显式“重新加载快捷键”或重启。菜单必须说明该边界。
- 恢复默认按 §8.2 处理；恢复全部先显示影响并确认，允许备份。导入识别 schema 和差异格式，先预览、再验证，不将有效目录当作用户差异。
- 原子写、配置锁及失败恢复复用现有机制；不得为了快捷键创建第二套竞争写入逻辑。

## 9. 帮助、提示与鼠标入口统一

所有快捷键展示从 `bindings_for(command, context)` 读取有效集合，经过同一格式化器输出。

- 菜单与完整帮助显示全部有效绑定；窄底栏显示首选键，多个按键不挤占功能名。
- 无绑定显示“未绑定”，不用旧默认值误导用户。
- 已删除绑定及备注在管理页中可见，日常提示只显示有效键；首选变化不改变匹配。
- 英文/中文只翻译功能名、说明和状态，不翻译键盘协议名、命令 ID 或配置字段。
- 键盘调用和鼠标点击调用同一个业务命令及 `enabled` 判断；不能在鼠标回调中构造“默认 F3”或默认字符来曲线调用。
- 历史文档保留当时事实；README 与当前操作帮助在代码落地时同步更新。本设计稿不能被引用为菜单已经存在的证据。

## 10. 外部软件与 Windows Terminal 的边界

### 10.1 后台软件的全局热键

Windows 的 `RegisterHotKey` 面向系统级快捷键，包含修饰键与虚拟键，触发后向注册目标发送 `WM_HOTKEY`。DevTabs 内部增加一个同名绑定，不能保证重新获得该事件。[R11]

因此本设计：

- 采用多个明确绑定和可自定义配置，不默认抢占。
- 不通过反复尝试 `RegisterHotKey` 探测全部按键占用；失败不等于可靠定位了某个软件，探测也不应干扰用户热键。
- 内部冲突由配置准确计算；外部占用只接受用户备注和实际测试，状态不能混写成“已检测到冲突”。
- 低级键盘钩子确有阻断后续传递的能力，但会改变外部应用行为且存在链路和超时要求，不纳入本次默认方案。[R12]

### 10.2 Windows Terminal 自身绑定

Windows Terminal 的动作/键位绑定可以在 DevTabs 之前消费输入。用户确有需要时，可以手动调整冲突项，或按官方方式使用 `unbound`。[R10]

DevTabs 管理菜单提供兼容说明和按键测试，但不自动改用户 Terminal 配置，不承诺仅影响一个标签页，不将 Ctrl+Fn 宣称为 Terminal 永远不会占用的组合。

### 10.3 验收用语

- 可承诺：“F3、Ctrl+F3 都已绑定同一命令，只要按键到达当前有效区域就可执行。”
- 不可承诺：“有了双绑定就能自动解决所有外部冲突。”
- 可承诺：“切换作用域后由当前区域命令解释按键。”
- 不可承诺：“软件知道这次 F3 是想截图还是编辑便签。”

## 11. 实施阶段与改动边界

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |

| 2：终端与管理闭环 | 前缀/原键发送命令、可配置占用、差异配置、管理 UI、录制、按键测试、首选显示、恢复/导入导出 | 第一个可使用版本就能发送原始 Ctrl+G/Ctrl+P，删键/改键/取消/失败可验证 |

这些阶段是完整交付的依赖顺序，不是按工作量删减功能。可以分批提交，注册框架、菜单、录制、测试、导入导出均保留范围；每个可用构建明确已迁移区域，终端原键出口和输入配对不能拖到最后。最终发布满足所有完成条件。

本次不要求改 IPC、停止宿主/Agent、重建 PTY、修改外部软件配置、安装键盘钩子或重做现有界面布局。

## 12. 测试与验收

### 12.1 生产分支自动审计与升级前后差异

规划新增 `tests/shortcut_source_audit.rs` 和 `tests/fixtures/shortcuts/production-key-uses.toml`。这是待实现测试与夹具路径，不表示本次文档更新已经落地代码。

1. 扫描 `src` 的生产 Rust 代码，排除 `#[cfg(test)]`、测试函数及专用测试模块；不能因测试与生产同文件就整文件忽略。
2. 优先用 Rust AST 提取按键/修饰键判断和模拟键盘命令调用，识别限定路径、use 别名及 match guard；以文件、所属 item 和归一化语法指纹定位，避免依赖易漂移行号。
3. 每处归类为 `registry`、`terminal-encoding`、`native-widget`、`protocol`、`recovery` 或迁移期 `pending-migration`，并记录理由；本地业务处理项还需关联 command ID。
4. 新的未登记站点、已有指纹改变、过期清单项、未知分类一律使审计失败；禁止 `src/sidebar.rs` 整文件放行这种宽泛白名单。更新清单必须可在差异中看到具体行为和理由。
5. pending-migration 只能随迁移减少，最终为零。registry 之外残留自有业务匹配须有明确控件/协议原因，不能用“legacy”永久豁免。
6. AST 检查不是 Rust 完整语义分析；宏生成和复杂别名要有显式登记与注册测试。用夹具验证“新增生产 F12 分支失败”“别名 KeyCode 不漏检”“只新增测试分支不误报”“删除分支后旧清单失败”。

规划新增 `tests/shortcut_regression.rs`：改动前在隔离业务 handler 的条件下捕获动作/消费结果，改动后用新 resolver 跑同组业务场景，枚举常用键及 Ctrl/Alt/Shift 组合、代表性焦点和模态状态。输出 `artifacts/shortcuts/keymap-before.json`、`keymap-after.json`、`behavior-changes.md`。报告包含原键、前后结果、受影响区域、有意修正的理由和替代按法；不把旧 resolver 留在新版本生产代码里，不要求读取旧配置。

例如总览 Ctrl+Alt+F3 原来可能因只判断 F3 而开便签，精确化后不再触发；这种变化必须进入发布说明，不能只写“兼容原快捷键”。只自动比较已捕获的基线场景，不宣称穷尽全部运行状态。

终端契约测试从注册表导出占用列表，并独立断言默认占用来源仅为受管前缀入口，防止新增注册项被测试无条件放行；键值读取注册表，不在测试里复制一套匹配规则。允许默认 Ctrl+G 的本地行为，并对 Ctrl+P 等清单外事件做字节/目标/次数断言；所有用户新增终端绑定也进入同样的有效表，并与默认清单区分来源。

### 12.2 纯逻辑与配置

- F3/Ctrl+F3 是两条可独立删除的绑定；Shift+F3、Ctrl+Alt+F3 不因主键相同被误匹配。
- 同命令重复绑定去重；冲突替换只影响指定键与区域；不同互斥区域可复用。
- add/remove、删除备注、disabled、preferred、恢复默认、默认值增删、用户绑定冲突、未知命令、非法格式、重复条目、快捷键段缺失和不支持的根 schema 都有明确测试；不测试旧格式迁移。
- 组合键大小写、Shift+Tab、字面 Plus、控制字符、布局字符、AltGr、IME 和粘贴不误识别。
- 前缀与独立键的歧义被拒绝；失焦、无效后续键、切任务、Esc 取消后不重放终端输入。
- 保存失败、并发写配置、取消、恢复默认、导入冲突均保留正确有效表。

### 12.3 路由与输入保真

- 总览 F3/Ctrl+F3 编辑便签；源码编辑器 F3/Ctrl+F3 下一处匹配；两者不互相触发。
- 输入框普通字母、中文、标点和剪贴板正文不触发背景命令；Ctrl+S 在编辑器保存文件而非保存预设。
- F3/Ctrl+F3 在未注册本地处理的终端区按原通道转发；Ctrl+C、Ctrl+Z、Tab、Enter、Alt、功能键及 release/repeat 行为不回归。
- 模态、录制、按键测试、未保存提示和移动缩放状态不向背景或 PTY 泄漏输入。
- 长按切换/启动命令只执行一次；导航允许连发；焦点改变不出现粘住的修饰键。
- Ctrl+G → Ctrl+G 恰发送一次原 Ctrl+G；Ctrl+G → g 仍轮次审阅，按住第一次 Ctrl+G 不误发送，长按第二次也不连发；Ctrl+P 默认直接透传，另测用户启用本地绑定后的可选发送出口。
- 逐步覆盖 §4.3 六条轨迹和补发去重，测试每个目标的 Down/Up 集合；纯修饰键、失焦、重连和旧会话释放不能仅靠最终 UI 快照验证。
- 所有键盘和鼠标入口执行同一命令 ID，修改/删除键位后鼠标仍可用。
- 危险操作、三秒限制、批量启动审阅及任务目标验证不被新分发器绕过。

### 12.4 管理菜单与显示

- 中英文、明暗主题及窄宽窗口都能查找、添加、修改、删除、恢复、应用、取消。
- 录制 Esc/Enter 不导致无法完成或退出；每个录制操作有鼠标确认/取消入口。
- 菜单、F1 帮助、底栏、工具提示按同一有效表更新；无绑定与用户删除状态准确；默认 Ctrl+F3 显示在前。
- 同一命令两条绑定都可用，长集合截断后仍能展开查看。
- 测试界面不执行命令、不写 shell、不持久记录键盘内容，未收到事件不捏造诊断结论。
- 从按键测试结果一键设首选，保留原绑定；无法录到的键仍能文本编辑；高风险系统/输入法组合的录制、文本输入和导入得到同一警告。

### 12.5 Windows 真机矩阵

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 无外部拦截 | 总览分别按 F3、Ctrl+F3 | 均打开同一便签功能，各只执行一次 |
| 截图软件 F3 全局热键 | 保留双绑定，按 F3 和 Ctrl+F3 | 根据实际拦截记录 F3 是否到达；Ctrl+F3 未冲突时执行便签，不保证 F3 独占 |
| 只希望 F3 截图 | 删除选定命令/区域的 F3，并附备注 | 对应本地命令不执行，其他区域独立；Ctrl+F3 仍有效 |
| Ctrl+F3 也被占用 | 添加自选无冲突组合并测试 | 不删除原两个键，新键可直接执行 |
| Terminal 拦截 | 为测试环境设置一个冲突 Terminal 动作 | 测试界面诚实显示未收到；其他别名仍可用；用户手动解除后原键可恢复 |
| 输入法与文本 | 终端/编辑器中输入中文并切换输入法 | 不抢占已保留组合，不误执行业务命令，不丢上屏文本 |
| 原生终端程序 | PowerShell、Codex、Claude 常见交互 | 未注册键继续透传，原始功能和重复/松开正常 |
| Claude Code 外部编辑器 | 在终端双按 Ctrl+G；另测删除本地入口后直接 Ctrl+G | 记录原键送达与外部编辑器结果，首个 G 不误入轮次审阅 |
| 终端 Ctrl+P | 默认直接按；另测用户将 quick_open 扩展到终端后使用原键出口 | 默认无需配置即能调用 CLI 功能；自选绑定有出口，文件区域查找不受影响 |
| Win32 输入粘键回归 | 按住 Ctrl/Alt 切面板、开关弹窗、切出窗口、断开重连 | 原目标事件平衡，无旧 release 泄漏到新目标，复焦后普通输入无粘住修饰键 |
| 切出 DevTabs | 切到其他应用按截图/输入法键 | 本重构没有新增系统级抢占，不改变其他应用热键行为 |
| 多前端配置 | 窗口 A 修改，窗口 B 显式重新加载 | 配置其他字段不丢失，各窗口生效状态可解释 |

外部软件/Terminal 测试只能在隔离测试配置或用户主动配置下进行；不为运行测试自动覆盖真实全局热键或宿主设置。

以下为 2026-11-14 查询的官方文档或官方仓库资料。外部事实与 DevTabs 的设计选择分开列出；在线文档和主分支会演进，实施与真机验证还须记录所安装的具体版本。没有依据搜索结果推断本机某软件已占用按键。

### 14.1 同类项目

| 来源 | 已核实的做法 | 本设计采用与取舍 |
| --- | --- | --- |
| [R1] Claude Code：交互模式 | Ctrl+G 打开默认文本编辑器；Ctrl+P/Ctrl+N 用于光标或历史导航，依输入位置而定 | 将 Ctrl+G 原键出口列为必做，并覆盖终端 Ctrl+P；CLI 的功能键位以安装版本为准，不猜测 Agent 意图 |
| [R2] WezTerm：按键分配与 Leader | leader 形成显式模式；官方例子用 leader 后 Ctrl+A 的 SendKey 向终端发送原 Ctrl+A | 采用受管前缀和显式发送动作；默认无超时是 DevTabs 的选择，不照搬其默认 1 秒超时，也不在取消后重放未知序列 |
| [R3] tmux：手册 | send-prefix 是发送前缀到应用的独立命令；默认前缀后 C-b 执行该命令 | 采用可命名、可点击、可测试的 terminal.send_prefix，而非把透传藏在字符分支顺序中；不照搬其默认前缀键 |
| [R4] VS Code：键盘快捷键 | 命令 ID、when 作用域、同键查询、录制/编辑、排障日志；用户可叠加绑定并用 -command 移除默认项 | 采用命令中心、有效表、用户差异和按键诊断；采用有限上下文而非脚本式 when，不照搬从下往上首条命中策略，也不默认记录普通输入 |
| [R5] Ghostty：自定义绑定 | unconsumed 可执行后继续发送；performable 按动作可执行性决定是否消费；ignore 与 unbind 语义不同 | 采用明确消费结果及“删除绑定”和“吞键”的区分；DevTabs 业务命令执行即消费，避免一次按键产生 UI/shell 双重副作用 |
| [R10] Windows Terminal：Actions | 命令与键位分离，同动作允许多个绑定，支持解除宿主绑定 | 采用一个命令多个绑定及点击直接执行；宿主修改由用户完成，不自动改 settings.json，也不把 Ctrl+Fn 当作一定安全的组合 |

这些项目提供的是可借鉴机制，并不能证明 DevTabs 已正确实现配对、序列或透传。相关正确性仍由 §4.3 的状态迁移、§12 的测试和本机协议实测证明。

### 14.2 平台规则核实

| 来源 | 核实结果与设计影响 |
| --- | --- |
| [R6] Windows 常用快捷键 | Ctrl+F4 常用于关闭支持多文档应用中的活动文档；Alt+F4、Alt+Tab、Ctrl+Space、Win+Space 等有系统/输入用途。由此逐项审核别名，并列出风险；不声称 Ctrl+F4 在所有程序中都是同一动作 |
| [R7] 微软简体中文输入法 | Shift 切换中英文模式，Shift+Space 切全/半角，Ctrl+Period 切标点；候选框还使用 Space/Enter/Esc/方向键。避让既有输入法功能，文本和候选选择不能被背景命令抢走；具体设置允许用户调整 |
| [R8] KEY_EVENT_RECORD | 提供按下/松开、重复次数、虚拟键、扫描码、字符及控制状态；ENHANCED_KEY 位区分扩展键。账本使用原始字段，不把 KeyCode 当作完整物理身份 |
| [R9] GetAsyncKeyState | 最高位表示当前按下；最低位不可靠，返回 0 也可能为调用失败。只用于挂起键的辅助核对，不作为“已收到 Up”或完整状态恢复的证明 |
| [R11] RegisterHotKey | 定义系统级热键，触发 WM_HOTKEY；注册可因占用等原因失败。内部绑定不能替代系统事件到达，也不能靠失败结果可靠识别占用软件 |
| [R12] LowLevelKeyboardProc | 低级钩子可通过返回值阻止后续传递，并有回调链与超时约束。本设计使用应用内路由，不安装钩子抢占外部热键 |
